# 资料准备与导入规范

本文件说明如何为 MineGuard Agents 准备案例、规程、支护方案和资源台账，并在前端“矿方资料与参数配置 · 阈值、案例、支护与资源”展开框中导入。另附开发者使用的离线标注资料说明。现有文件名保留以兼容链接。

## 1. 资料类型总览

| 资料类别 | 用途 | 推荐格式 | 导入位置 |
| --- | --- | --- | --- |
| 事故案例 | 为知识检索提供可追溯的历史案例和处置经验 | JSON、PDF、DOCX、TXT、Markdown | 配置框的案例类别 |
| 规程与制度 | 支持条款检索、动作约束和审批依据 | PDF、DOCX、TXT、Markdown | 配置页面的“规程与制度” |
| 支护方案 | 提供动作顺序、责任岗位、时限和资源需求 | 结构化 JSON，正文可附 PDF/DOCX | 配置页面的“支护方案” |
| 资源台账 | 核对人员、材料和设备的可用数量 | CSV 或 JSON | 配置页面的“资源台账” |
| UIE 标注数据 | 用于知识抽取模型训练或离线评估 | CSV、JSONL | `真实数据投喂/02_UIE标注数据/` |
| 原始监测数据 | 触发实际数据工作流 | JSON、CSV 或前端文本摘要 | “原始监测记录”或自定义输入 |

公开文献与事故原文属于参考资料；`tests/fixtures/actual_ingestion/` 是软件测试资料，两者用途不同。实际数据任务使用用户配置选定的资料；更换资料后保存新配置版本，任务会冻结本次使用的资料快照。单份上传不超过 20 MB，知识正文不超过 500000 字符。YAML、HTML、图片、旧版 DOC 和 Excel 不能直接通过此配置入口解析，需先转换成支持格式。

## 2. 统一登记信息

上传时填写下列元数据。前端自动使用文件名作为标题；API 调用时将元数据作为 `/api/configuration/ingest` 的 multipart `metadata` JSON 字符串，并将原文件放在 `file` 字段。元数据与正文分开提交。

| 字段 | 要求 |
| --- | --- |
| `mine_id`、`roadway_id`、`area` | 矿井编号、巷道编号、测区；与任务完全一致 |
| `category` | `case`、`regulation`、`support` 或 `resources` |
| `title` | 文件名或正式资料名称 |
| `source` | 来源文字，建议包含发布机构、URL 或内部授权编号 |
| `version` | 资料版本或修订号 |
| `observed_at` | 资料时间；台账填写库存观测时间，使用含时区的 ISO 8601 |
| `valid_from`、`valid_to` | API 可选适用期，须同时填写且包含时区 |

发布日期、页码、条款号、OCR 复核说明等可以写入正文和本地来源清单；它们不是上传 API 的独立字段。不要向正文 JSON 添加未定义字段。

来源登记用于追溯，不代表系统自动认可资料的现场适用性。法规、企业制度和现场方案仍应由有权限人员确认。

## 3. 事故案例格式

前端下载的“知识资料模板”使用 `text` 和 `terms`，例如以下占位模板。替换尖括号内容后上传，调查报告中的事后救援和整改要求应保持原意，不自动转成本次处置动作。

```json
{
  "text": "<报告名称、发布机构、原始地址、页码；事故经过、原因、前兆、处置和后果的核对摘要>",
  "terms": ["顶板", "支护"]
}
```

仓库的案例整理工具另有 YAML 归档格式，下例仅解释归档字段，不能直接上传到前端：

```yaml
case_id: real-2024-001
location: 某矿某采区某工作面
occurred_at: "2024-10-23T04:20:00+08:00"
risk_level: orange
causes:
  - 原报告中的原因一
precursors:
  - 原报告中的前兆或监测现象
actions:
  - 预警触发后采取的处置动作
outcome: 原报告中的人员和设备后果
lessons:
  - 原报告中的整改要求
source: 发布机构及报告名称
metadata:
  source_url: https://example.org/report
  published_at: "2024-11-01"
```

要求：

- `case_id` 在资料库内唯一；真实案例建议使用 `real-YYYY-NNN`。
- 归档 `risk_level` 是整理标签，必须记录映射依据；事故伤亡等级不能等同于当前测区的预警等级。
- `causes`、`precursors`、`actions` 使用原报告或可追溯的整理结果，不编造能量、频次和伤亡数字。
- 保留报告原始动作语境，不把事后救援改写成事前预警指令。本次执行动作应来自另行上传并选定的结构化方案。
- 缺少量化数据时写清“报告未提供”，不要用估计值填充。

模板和已整理示例位于 [`真实数据投喂/01_事故案例整理/`](../真实数据投喂/01_事故案例整理/)。其中的 Python 脚本用于复现格式转换，不是用户必须执行的步骤。

## 4. 规程与制度格式

规程可以直接上传 PDF、DOCX、TXT 或 Markdown。也可整理成知识 JSON，将版本、条号和出处写入正文；以下为字段占位模板，不是法规引文：

```json
{
  "text": "<资料名称、版本、条号、原文、适用范围与出处>",
  "terms": ["顶板管理"]
}
```

扫描 PDF 需要先 OCR 并人工校对。系统会保存原始文件哈希和提取文本，但不会把上传文件自动标记为“正式法规”，也不会根据普通叙述猜测审批权限。

## 5. 支护方案格式

支护方案需要同时说明正文、动作和资源需求。资源名称和单位必须与台账一致。以下数量和动作仅展示格式，应替换为本次批准方案的内容：

```json
{
  "text": "本矿本测区方案正文及适用条件",
  "terms": ["顶板离层", "锚索"],
  "actions": [
    {
      "sequence": 1,
      "action": "加密顶板观测",
      "owner_role": "安全监测员",
      "deadline_minutes": null,
      "requires_approval": true,
      "acceptance_criteria": ["完成现场记录并由负责人复核"]
    }
  ],
  "requirements": [
    {"group": "equipment", "name": "顶板离层仪", "required": 2, "unit": "台"}
  ]
}
```

`deadline_minutes` 为 `null` 时表示原资料未规定时限；系统不会自行补充演示时限。`requirements.required` 必须是正数，动作序号不能重复。

## 6. 资源台账格式

CSV 表头必须为：

```text
group,resource_id,name,available,required,unit
```

`group` 只能是 `personnel`、`support_materials` 或 `equipment`。JSON 形式使用相同字段：

```json
{
  "personnel": [
    {"resource_id": "person-001", "name": "安全监测员", "available": 2, "required": 1, "unit": "人"}
  ],
  "support_materials": [],
  "equipment": []
}
```

服务端会拒绝空名称、负数、NaN、重复资源编号和单位不一致的记录。`available` 是经过核实的可用量；未返回可用量的业务接口不能当作零库存。台账必须填写观测时间和来源，过期台账不会被静默使用。

## 7. UIE 标注数据格式

CSV 使用以下八列：

```text
text,entity,entity_type,relation,object,object_type,confidence,source
```

`object` 必须逐字出现在 `text` 中，`object_type` 必填；拿不准的主语或关系可以留空。实体类型为：地质构造、支护设备、顶板灾变、监测指标、处置规程、岗位角色、巷道分区。关系类型为：诱发、支护、防控、监测、调度、上报、传导。

模板和示例位于 [`真实数据投喂/02_UIE标注数据/`](../真实数据投喂/02_UIE标注数据/)。UIE 文件不是运行实际数据任务的必需项；只有配置了相应抽取或评估流程时才会参与模型处理。

## 8. 导入和校验流程

1. 展开“矿方资料与参数配置 · 阈值、案例、支护与资源”，填写矿井编号、巷道编号、测区、资料来源、版本和资料时间。
2. 按类别上传文件或填写结构化 JSON/CSV。
3. 通过“上传并解析所选类别”选择文件，服务端自动解析和校验，成功后显示“已上传 · 已校验 · 已入库”。
4. 勾选本次资料，使用结构化方案时在“选定适用方案”中选中它。填写配置有效期、统计窗口和规则，点击“保存配置到后端”。
5. 使用“预检”查看适用时间、字段、资源名称和资料范围是否匹配。
6. 启动 `scenario_id=custom` 的实际数据任务。
7. 在结果的 evidence/provenance 中检查输入字段、配置版本、文件哈希、库存来源和运行编号。

运行启动时会冻结配置快照。之后保存新配置不会改变已归档结果；需要新资料时保存新版本并重新运行。

## 9. 资料如何进入六 Agent

| 节点 | 资料使用方式 |
| --- | --- |
| 感知预警 | 读取监测输入和适用的规则参数，输出统计、异常和方法依据 |
| 知识检索 | 检索本次配置选定的案例、规程和支护方案，并保留来源 |
| 调度决策 | 使用结构化方案动作、责任岗位、时限和审批要求 |
| 资源评估 | 使用本次冻结的台账或业务库存快照，逐项比较需求与可用量 |
| 协同管控 | 在身份、通知和工单接口已配置且获得授权后提交业务请求 |
| 反思迭代 | 使用后续观测、执行回执和同口径指标计算变化 |

普通文件只提供可检索的证据，不会自动生成未在资料中出现的动作、资源数量或审批结论。

## 10. 质量与授权要求

- 只上传有权使用和分发的资料；公开资料保留原始来源和访问日期。
- 原始报告、法规和企业内部文件分别注明发布机构和适用范围。
- 代码格式校验通过不等于现场参数已经标定；矿方阈值、模型置信度和执行权限仍需专业确认。
- 不要把个人凭据、业务接口密钥、未脱敏人员信息或真实 `.env` 提交到 GitHub。

更具体的配置、API 和验收步骤见 [实际数据配置指南](actual-data-guide.md)。公开来源和版权说明见 [公开资料来源与导入说明](资料爬取任务书.md)。
