## 2. 任务二：UIE 标注训练数据（唯一需要你人工投入的活）

**目的**：让微调后的 UIE 模型能从灾变文本抽「实体+关系+SPO 三元组」，喂给 LLM→KG 写回链（knowledge_candidates → 审核门 → Neo4j）。**模型微调、接入、评估全由我做，你只负责标数据。**

### 2.1 需要你给什么
- **标注数据 200-500 条**（保底 200，建议 300-500），**可分批**（先 30-50 条验证格式）。
- 语料全部本地：18 份事故报告 + `deploy/ragflow/docs/real` 160 份（规程 72 / 支护 64 / 事故 24）。**PDF/HTML 我转好纯文本再标，勿直接标乱码。**

### 2.2 怎么做（6 步流程）

> 一句话：选一段原文 → 实体表里定 object → 判关系 → 填一行 CSV → 推进度。每条 2-5 分钟，200 条约 8-15 小时，每天 1-2 小时分两周。

1. **选语段（text）**：1-3 句、自包含、含具体实体。最佳章节：报告「事故发生经过/现场勘查/原因分析/整改措施」、规程条款、支护方案正文。反例：无实体的程序句（「相关人员立即到岗」）、>4 句长段、条款编号头。
2. **定 object（必填）**：从 text **逐字复制**一个实体。一句话多处可标 → **一条一行**（同一 text 可拆多条）。找不到就换段，宁缺毋滥。
3. **定 entity + entity_type（推荐）**：句子里「发起动作」的主语（锚杆/离层仪/班长/岩层）；没有明确主语 → 留空。
4. **判 relation（推荐）**：对照 2.4 决策表；拿不准写「一句话关系描述」，我按 7 类白名单映射。约 90% 落在 诱发/支护/监测。
5. **估 confidence**：0.9-1.0 原文直白断言、对象唯一；0.7-0.8 能推断但不直白；0.5-0.6 模糊需跨句；不认识的留空不标。
6. **填 CSV 存盘**（模板已备，见 2.5）。

### 2.3 要求（7 条）
1. **object 必须逐字出现在 text 里**——训练干净度硬规则（代码只硬校验 object_type，逐字规则保证数据质量+写回不拒）
2. object_type / entity_type ∈ 7 类；relation ∈ 7 类（或写关系描述）
3. confidence 为 0-1 数字
4. source 填文档名
5. 同篇文档内同一词类型一致（如「顶板离层」在监测语境统一标 监测指标）
6. **不编造量化数值**（报告没写能量/频次就写「能量异常」，不写数字）
7. 只标真实文档正文；仿真案例标 HALLUCINATION 且不进训练集

### 2.4 实体/关系速查

**实体 7 类**（object_type / entity_type 唯一依据）：
| 类别 | 是什么 | 真实示例 | 反例 |
|---|---|---|---|
| 地质构造 | 静态地质体 | 顶板、粉砂岩、泥岩、破碎带 | 「顶板垮落」→顶板灾变 |
| 支护设备 | 承力构件 | 锚杆、锚索、托盘、托板、支架 | 「锚杆支护设计」→处置规程 |
| 顶板灾变 | 灾害现象 | 垮落、冒落、片落、帮鼓 | 「顶板离层」读数→监测指标 |
| 监测指标 | 监测数据/设备 | 离层仪、微震能量、b值、应力 | 「顶板明显下沉」→顶板灾变 |
| 处置规程 | 措施/制度/条款 | 支护设计、作业规程、找掉 | 设备名→支护设备 |
| 岗位角色 | 人员角色/工种 | 班长、司机、值班员 | — |
| 巷道分区 | 巷道/区域位置 | 运道、迎头、工作面、切眼 | 岩层名→地质构造 |

口诀：**现象→顶板灾变；读数/设备→监测指标；承力构件→支护设备；静态岩体→地质构造；措施条款→处置规程。**

**关系 7 类**（A --关系--> B）：
| 关系 | 语义 | 判断入口 | 例句 |
|---|---|---|---|
| 诱发 | A 引发/导致 B | 造成/导致/致使 | 岩层 → 冒落 |
| 支护 | A 支撑/加固 B | 支护/加固/锚固 | 锚杆 → 顶板 |
| 防控 | A 防治/防控 B | 防/加固/卸压/撤人 | 测点 → 冒顶 |
| 监测 | A 监测/观测 B | 监测/观测/显示 | 离层仪 → 顶板 |
| 调度 | A 指挥/安排 B | 指挥/安排/组织 | 班长 → 找掉 |
| 上报 | A 上报/报告 B | 上报/汇报/通知 | 值班员 → 预警 |
| 传导 | A 波及/传播 B | 波及/传播/蔓延 | 垮落 → 巷道 |

## 附 B：UIE 契约 + 训练数据格式 + 验收（代码实测）

**候选字段**（`knowledge_candidate_tool.py` → `review_candidates.py` → `knowledge_sources.py`）：candidate_id（kc-{run_id}-{reflection_id}-{i:03d}）/ entity / entity_type / relation / evidence / source / confidence（0-1，默认 0.5）/ review_status（入队固定 pending_review）/ reflection_id / workflow_run_id / created_at / object / object_type / uie_enriched / reviewed_by / reviewed_at / rejection_reason
**写回字段全集**：`{entity, entity_type, relation, object, object_type, evidence, source, confidence, reviewed_by, reviewed_at}`

**UIE 模型 I/O**（`uie_extractor.py:142-166`）：输入候选（读 entity/relation/evidence），输出 `{object, object_type, confidence, evidence}`。object_type 越界 → 抛 `UIEExtractionError`；object 为空 → 计 failed、保留待补、写回被拒。
> **诚实注**：代码没有「object 必须出现在 evidence 原文」的强校验，仅 `_SYSTEM_PROMPT` 约束。我们把「逐字出现在 text」定为**标注质量硬规则**，但代码只硬校验 object_type。

**训练数据格式**：交付推荐 CSV（8 列）`text,entity,entity_type,relation,object,object_type,confidence,source`；训练最终格式 JSONL（我自动转）：
```jsonl
{"text":"<原文证据>","entity":"<主语，可空>","entity_type":"<7类之一，可空>","relation":"<7类之一，可空>","object":"<宾语，必填>","object_type":"<7类之一，必填>","confidence":0.9,"source":"<文档名>"}
```
**覆盖度目标**：实体——地质构造 50 / 支护设备 40 / 顶板灾变 40 / 监测指标 30 / 处置规程 30 / 岗位角色 20 / 巷道分区 20（小计 230）；关系——诱发 40 / 支护 30 / 监测 30 / 防控 20 / 调度 15 / 上报 10 / 传导 10（小计 155）。合计 ≈230 达保底，300-500 更佳；一条同时计入实体+关系目标。

**模型接入配置**：`EntityRelationExtractor` 直连 OpenAI 兼容 `/chat/completions`（temperature 0.0），读 `OPENAI_BASE_URL`（默认 https://api.deepseek.com/v1）、`OPENAI_API_KEY` 或 `DEEPSEEK_API_KEY`、`model=LLM_QWEN_MAX 或 LLM_MODEL_NAME`；富化开关 `UIE_ENRICH_KNOWLEDGE_CANDIDATES`（1/true/on/yes）。**微调接入** = vLLM/Ollama 起本地端点 → `OPENAI_BASE_URL` 指本地 + `LLM_QWEN_MAX` 设微调模型名，代码零改动。

**验收**（`validate_uie_phase8.py` 5 项）：① 7 类实体枚举 + 缺 key 抛 UIEExtractionError；② JSON 宽松解析（裸 JSON/```json 围栏/裸围栏）；③ apply_review 决策打标（approve/reject/skip + reviewed_by/reviewed_at）；④ write_approved 写回链路（approved+完整 SPO 落图、缺审核人拒写、缺 object 拒写、Cypher 核验）；⑤ extract_object 端到端（在线，object 非空 + object_type ∈ 7 类）。
